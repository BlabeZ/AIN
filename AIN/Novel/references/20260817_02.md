有了这批文件后，我对“项目结构”的评价会明显提高：**你已经在从“小说资料夹”往“轻量级小说数据库/创作工程”走了。** `bible → characters → outline → state → chapters` 这个方向非常适合长篇幕后流，尤其你的故事还涉及多身份、伏笔、等级、地点和势力交叉，纯靠作者记忆迟早会炸。`AGENTS.md` 里要求创作前核对设定、创作后更新状态，这个工作流本身是正确的。

但现在也到了一个分水岭：**如果继续加 JSON，而不先规定“谁才是真相”，项目以后会出现一种很麻烦的情况——文件越来越全，反而越来越不知道该信哪个。**

## 一、现在最值得保留的是“静态设定”和“动态状态”分层

目前其实已经隐约形成了两个层级。

`bible/` 解决的是：

> 这个世界原则上是什么样？

比如力量等级怎么计算、协调局是什么、研究院从哪里来、火星殖民是什么性质。

而 `state/` 应该解决：

> 故事写到当前这一章时，世界现在是什么样？

例如研究院修复度为0、关明衡当前在学校、周磊当前失踪、某条伏笔是否已经真正埋下。

这是非常好的设计。

研究院的 JSON 已经比较接近这个思路：有 `status: damaged`、`recovery: 0` 等动态字段。

问题是现在静态信息又被抄进了状态文件。例如研究院 JSON 同时再次写了“万法解析”“与地球力量体系无因果”“复现型能力同频”等内容，而这些其实已经属于 `world.md / power_system.md` 的永久设定。

久而久之非常容易出现：

`world.md` 改了。

`研究院.json` 忘了改。

然后 AI 创作前两个都读取，开始猜哪个是真的。

所以我建议立一条非常重要的工程规则：

> **Bible 存规则，State 只存变量。**

比如研究院状态文件最好最终接近：

```json
{
  "item": "研究院",
  "status": "damaged",
  "recovery": 0,
  "unlocked": [],
  "known_memory_fragments": [],
  "current_host": "关明衡",
  "last_updated_chapter": 0
}
```

而“它为什么绑定主角”“它能解析魔法与科技”“未来能开传送门”，都不应该重复存在于 state。

这样结构会干净很多。

# 二、当前最严重的问题：`state` 混淆了“计划发生”和“已经发生”

这是我看完补充文件后认为最需要立即修改的地方。

例如现在 `foreshadowing.json` 里：

f001 是第1章埋；

f002 是第3章埋；

f004 是第二卷埋；

f005 是第三卷埋；

f006 是第三卷末埋。

但它们全部都是：

`"status": "open"`。

问题在于目前正文第一、二章还是待写。

因此严格来说：

**f006根本还没有“open”。**

它只是“计划将来埋”。

这对作者本人也许没问题，但对以后协助创作的模型非常危险。

因为当它看到：

```json
{
  "id": "f006",
  "status": "open"
}
```

它很容易理解成：

> 百面接受契约国际招揽这件事已经在正文中发生，只是还没回收。

但实际上那是三十多章之后的规划。

所以这里我非常建议把伏笔状态正式区分为：

```text
planned
↓
planted
↓
developing
↓
paid_off

以及：
cancelled
```

这样：

f001正文没写以前：

`planned`

真正第一章写完六边形以后：

`planted`

中间得到第一层“同频”解释以后：

`developing`

大后期彻底揭示：

`paid_off`

这一个调整，会让整个项目的“计划层”和“事实层”一下清晰很多。

---

# 三、甚至可以再进一步：明确区分“Canon”和“Plan”

这是我最推荐的结构升级。

目前 `outline/` 明显是未来计划。

但 `state/` 里面已经开始掺入未来规划。

建议以后形成严格的数据流：

```text
Bible
世界运行规则
      ↓
Outline
未来准备怎么写
      ↓
Chapter
实际写出来了什么
      ↓
State
根据已经完成的正文更新当前事实
```

也就是说：

**Outline → Chapter → State。**

而不是：

**Outline → State → Chapter。**

这一点非常重要。

`state` 应该永远只描述**已经成为正文事实的东西**。

如果第18章原计划让某角色死掉，但临场改成没死，那么 outline 可以过期，但 state 绝不能提前写“死亡”。

这样以后甚至可以规定：

> `state/` 中不存在未来。

我认为这会非常适合你的项目。

# 四、现在 `foreshadowing.json` 和 `foreshadowing.md` 已经出现了“重复真相”问题

这组文件最能说明为什么需要收紧结构。

`foreshadowing.md` 文件头写的是：

> 状态以 JSON 为准，json 只存 id/状态/埋设点，两者配套使用。

但实际上当前 JSON 已经保存了：

`id`

`planted`

`hint`

`payoff`

`status`。

也就是说：

**文件自己定义的职责已经和实际 schema 不一样了。**

而且 f002 已经发生了内容漂移。

JSON 中的 f002 是：

> 第一卷第3章，周磊失踪，老师称转学但课桌没清空。

但 MD 中的 f002 又定义成：

> 第一卷末，协调局接手离奇失踪案；失踪者回来以后检测出异常异能残留。

实际上这是**同一主线的两个不同节点**。

这已经证明长篇继续发展以后，“双份记录同一事实”一定会漂。

我的建议是：

JSON负责机器需要查询的结构化字段：

```text
id
status
planned_plant
actual_plant
planned_payoff
actual_payoff
related_characters
related_factions
```

MD只负责：

> 这条伏笔应该怎么写、什么可以透露、什么不能透露、设计意图是什么。

不要在两个地方重复描述核心事实。

# 五、`locations.json` 现在混了两种完全不同的数据

现在里面既有：

> 关明衡 → 临江市第三中学

> 周磊 → 失踪

又有：

> 月球科考站集群 → 月球

> 火星殖民城市群 → 火星

> 平行宇宙殖民点 → 若干低魔/低科技位面。

前一种是：

**当前人物位置状态。**

后一种是：

**地点本身属于哪里。**

实际上后者已经属于 `bible/locations.md`。

所以我会把 `state/locations.json` 直接改成一个纯粹的：

**current_positions.json**

例如：

```json
{
  "关明衡": {
    "location": "临江市第三中学",
    "status": "present",
    "last_updated_chapter": 1
  },
  "关志远": {
    "location": "临江老城区",
    "status": "active",
    "last_updated_chapter": 1
  },
  "周磊": {
    "location": null,
    "status": "missing",
    "last_known_location": "临江市第三中学门口",
    "last_updated_chapter": 3
  }
}
```

这样它真正能完成你在 AGENTS 中说的那个用途：

> 防止人物瞬移和地点冲突。

月球、火星、黑市街在哪，就让 `bible/locations.md` 负责。

# 六、`timeline.json` 应该成为非常重要的文件，但目前还太弱

现在 timeline 只有：

> t001，第1章，午休觉醒；下午首次透视。

这其实还没有真正发挥时间线的价值。

而且现在：

```json
"date": "第 1 章"
```

严格来说不是 date。

最好拆开：

```json
{
  "id": "t001",
  "chapter": 1,
  "story_date": "故事第1日",
  "story_time": "午休",
  "location": "临江市第三中学",
  "participants": ["关明衡"],
  "event": "觉醒分身能力，研究院完成锚定",
  "visibility": "关明衡不知情"
}
```

为什么特别建议加强它？

因为你的小说以后有：

本体；

分身A；

分身B；

分身C；

地球；

火星；

平行世界。

而且可能同时行动。

到那时候真正会杀死连续性的不是“世界观忘了”，而是：

> 百面明明周三晚上在火星，为什么本体周三下午已经回收了他的记忆？

所以对于普通小说，timeline 是辅助文件。

对于**分身流**，timeline 未来会成为核心基础设施。

# 七、关系文件现在不是“设计不好”，而是明显还没有开始真正使用

目前 relationships.json 只有两条：

关明衡—关志远。

关明衡—主脑。

但人物卡里已经实际上存在：

关明衡—林小满；

关明衡—周磊；

关明衡—协调局；

百面—金水物业；

百面—契约国际；

神秘买家—同业会……

而这本小说未来最麻烦的地方还不是普通关系，而是：

**同一个人拥有多个身份以后，不同势力对不同身份拥有不同认知。**

所以关系系统真正应该追踪的不是简单的：

> A和B是什么关系？

而是：

> A认为B是谁？

这对幕后流非常关键。

以后最好存在类似：

```json
{
  "observer": "契约国际亚太分部",
  "subject": "百面",
  "relation": "外围合作人员",
  "trust": "medium",
  "knows_true_identity": false,
  "suspects": ["背后存在供货商"],
  "last_updated_chapter": 33
}
```

与此同时：

```json
{
  "observer": "协调局临江办事处",
  "subject": "关明衡",
  "relation": "特训生",
  "known_level": 1,
  "known_clone_count": 1
}
```

而作者真相则是：

```text
真实等级：2
真实分身数：2
```

你这本书非常适合把状态管理进一步发展成：

**真实状态 vs 他人认知状态。**

这是项目结构上最值得围绕核心卖点定制的地方。

---

# 八、建议增加一个非常小但非常有用的“当前快照”

AGENTS 目前要求每次创作前读取：

world、factions、power system、locations、characters、outline、state……

小说写到200章以后，这个成本会越来越夸张。

不应该每写一章就重新吞完整个世界圣经。

可以增加：

`Novel/state/current.json`

只记录非常少的东西：

```json
{
  "canon_through_chapter": 12,
  "current_arc": "arc_002",
  "story_day": 8,
  "hero": {
    "level": 1,
    "public_level": 1,
    "clone_count": 1,
    "public_clone_count": 1
  },
  "research_institute_recovery": 0,
  "active_plotlines": ["f002"],
  "current_locations_file_version": 12
}
```

它不是新的真相来源。

它只是一个**索引/快照**。

AI先看这个，就知道故事现在写到哪里，然后按需去读详细文件。

# 九、AGENTS.md 还缺一条最重要的东西：冲突时谁优先

现在 AGENTS 的原则是：

> 所有文档都必须一致。

理想情况下当然应该一致。

现实中长篇小说一定会出现冲突。

而目前你的第一章大纲、卷纲和伏笔文件就已经发生了一些版本漂移。

所以必须规定**优先级**。

我建议未来的权威层级是：

```text
已经定稿的正文
        ↓
Bible 世界硬规则
        ↓
State 当前事实
        ↓
角色卡
        ↓
分卷 / 剧情弧 / 单章大纲
        ↓
Ideas / 备选方案
```

这里有一个很关键的原则：

**Outline 是计划，不是事实。**

如果第40章大纲说A死了，但真正写正文时改成A活了：

不要修改正文去服从旧大纲。

而应该：

正文成为事实 → 更新 state → 修改后续 outline。

当然，如果正文无意违反了世界硬规则，那就应该先判断是正文 bug 还是正式 retcon。

因此我甚至建议再增加一个很小的：

`decisions.md` 或 `retcons.md`

专门记录正式设定变更。

比如：

> 2026-xx：分身评级由“数量决定等级”改为“能力质变决定等级”；旧大纲涉及之处统一按新规则解释。

长篇项目里这个文件以后会非常值钱。

```text

│
├── bible/
│   ├── world.md
│   ├── power_system.md
│   ├── factions.md
│   └── locations.md
│
├── characters/
│   ├── 关明衡.md
│   ├── 关志远.md
│   ├── 林小满.md
│   └── 周磊.md
│
├── factions/
│   ├── 协调局.md
│   ├── 金水物业.md
│   └── 契约国际亚太分部.md
│
├── outline/
│   ├── master_outline.md
│   ├── volumes/
│   │   ├── volume_01.md
│   │   ├── volume_02.md
│   │   └── volume_03.md
│   ├── arcs/
│   │   └── arc_001.md
│   └── chapters/
│       ├── 001.md
│       └── 002.md
│
├── chapters/
│   ├── 001.md
│   └── 002.md
│
├── state/
│   ├── current.json
│   ├── timeline.json
│   ├── current_positions.json
│   ├── relationships.json
```

其中最关键的不是目录名字，而是每层只有一种责任：

**Bible = 世界真理。**

**Characters/Factions = 实体档案。**

**Outline = 尚未发生的计划。**

**Chapters = 已经真正写出的故事。**

**State = 正文发生以后留下的当前世界快照。**

**Meta = 作者修改项目规则的历史。**

一旦这样划清楚，整个项目会非常稳。

## 我现在会优先改的五件事

1. 给所有 `state` 文件增加“**只记录已经发生的事实**”这一原则，未来剧情不得提前写入当前状态。

2. 把伏笔状态改成 `planned → planted → developing → paid_off`，解决目前所有未来伏笔都叫 `open` 的问题。

3. 解决 `foreshadowing.json / md` 的职责重叠，尤其 f002 已经出现的版本漂移。

4. 把 `locations.json` 改成纯“当前人物位置”，世界地点归回 Bible。

5. 在 AGENTS 里增加**文档冲突优先级**和“正文定稿后才提交 state”的规则。

做完这些，我认为就**不需要继续大量增加管理文件了**。再继续堆 schema 容易进入“为了管理小说而管理小说”。

真正值得继续深挖的只有两个数据结构：**timeline** 和 **他人认知状态**。因为这两样不是普通网文都需要，而是你的“分身+多身份+谍战”题材天然需要。它们会直接帮助剧情，而不是单纯让仓库看起来更专业。

从项目工程角度说，现在已经有不错的骨架；下一步应该做的是**减少重复真相，而不是增加文档数量**。
